# ChinaMobile-H13

中国移动「和对讲」专业版 H13（同硬件平台：泉盛 MAX 11）的设备研究资料。

本仓库保存对**自有设备**的离线分析成果：模块 MCU 固件、反汇编、分析脚本、
MCU 模拟器，以及历次开发用的 Android 工程与文档记录。

## 让 H13 发出程序提供的语音（2026-09-20 达成）

2026-09-20，H13 首次把**程序提供的音频**经 DMR 空口发出，对端 TYT 电台
听清了内容（"one two three four five"）。不是声学转录，是把语音数据直接
送进基带模块发射。本节记录完整做法与关键判据。

### 一句话结论

**模块自己会做信道编码。宿主必须送未经信道编码的 49 位 AMBE 参数，
而不是已编码的空口帧。**

此前十九次发射送的都是标准空口帧（已做 Golay/Hamming 纠错编码并交织），
模块把它们当作参数又编码了一遍。因为 Golay 是系统码、码字前段恰为基音、
增益、清浊等最重要的参数，对端仍能听出人声轮廓，却完全听不懂内容——
这正是长期观察到的"能辨出是人声、但不可懂"。

### 硬件与通路

```
Android (MSM8909, 8.1)  --ttyHS0 文本 AT-->  MCU 0.3.66  --HPI-->  SCT3258 基带
```

原厂发射全程由 MCU 驱动，上位机只下一条 `AT+DMOPTT=1`，音频取自模拟
麦克风通路。要送程序音频，必须绕过麦克风，经 HPI 把语音帧直接交给基带，
即厂商 PC 工具里的"外部编码发射"模式。

### 完整发射流程

#### 一、信道必须是明文

```
AT+DMOSETDIGITALCH=433550000,433550000,13,99,12345678,directmode,group,
                   slot1,slot1,off,low,8,2,2,99
```

第十项为加密开关。**必须是 `off`**。此前长期写成 `on`，模块会用密钥
`12345678` 把语音加扰，对端没有密钥，听到的一律是与内容无关的噪音——
这曾经掩盖了所有其它问题，详见 `docs/H13_new.md` 2.8.71。

#### 二、控制链（HPI，经 MCU SRAM 桥下发）

按顺序，每条等模块回执：

| 序 | 线上正文 | 含义 |
|---|---|---|
| 1 | `19 00` | CARRIER_LOST |
| 2 | `3e 60` | VOCODER_IO_SET = 外部编码**发射**（接收侧为 `0x0c`） |
| 3 | `02 18` | VOCODER_CMD_SET(24) |
| 4 | `6f <时隙>` | 时隙配置（包类型 5） |
| 5 | `18 02 00 00` | WORK_MODE_DUPLEX(2) |
| 6 | `1a 02` | PROCESS_MODE(2) |
| 7–11 | 见下 | 发射调制链五条编解码器寄存器写 |

**顺序要紧**：`3e 60` 必须在 `02 18` **之前**，与厂商
`Form_SaveVocoder.button_vocoder_in_out_Click` 一致；反了相当于在路由还
指向内部输入时就下了声码器命令。

调制链五条为包类型 `0x40`、正文 `{00, 页, 寄存器, 值, 00, 00}`，确认帧
正文为 `{0x17, 0x00}`：

| 页/寄存器 | 值 |
|---|---|
| P01 / R10 | `0x40` |
| P01 / R3B | `0x11` |
| P00 / R56 | `0xF3` |
| P00 / R57 | `0xBA` |
| P00 / R58 | 麦克风增益档位（取自设备表 `0x20002e25`） |

#### 三、呼叫头（两条，包类型 5）

```
43 <呼叫模式> 09 <9 字节语音链路控制>
呼叫模式：第一条 0x01，第二条 0x11
链路控制：[0]=0 全链路控制操作码  [1]=0 厂商标识  [2]=0 服务选项
          [3..5]=被叫地址  [6..8]=主叫地址
```

**服务选项必须为 0**。第 6 位（`0x40`）是 DMR 标准里的加密标志，置位会
让接收机按加密语音处理。

#### 四、语音数据（关键）

**先把音频编码成标准 AMBE，再把每帧的 49 位参数取出来重新打包。**

```
PCM 8kHz 单声道
  → AMBE+2 编码，得到 9 字节/帧的空口帧（已含 Golay/Hamming 与交织）
  → 解出每帧的 49 位参数（本仓库用 tools/ 下的解码器输出 ambe49 列）
  → 49 位按 MSB 在前左对齐填入 9 字节，余 23 位置零
```

三帧打成一个 27 字节单元，线上帧为：

```
包类型 3，正文 = 01 1b <27 字节>
                 ^^ ^^
                 |  +-- 长度 0x1b = 27
                 +----- 字段 1
```

长度取 **27**（DMR 每突发三帧）。厂商示例用 36 是因为那台设备的
`vocoder_output_len` 不同，照搬会把 27 字节单元按 36 字节切片，每个包都
跨在单元边界上。

#### 五、供数节拍

**发射态下模块只持续交帧、不发回执短帧**（无射频时才有回执，这点容易
误导）。因此：

- 模块每经 HPI 交出一帧（包类型 `0x20`、正文 `01 1b + 27 字节`），
  宿主就回送一帧。一对一。
- 交帧间隔即空口帧率，约 60 毫秒，速率会自动锁住。
- 按回执等待会把串口往返延迟串进时间轴，实测 68 单元被拉到 10.4 秒而
  音频只有 4.08 秒，对端完全无声。

#### 六、收尾

发终止呼叫头，再下 `VOCODER_IO` 关闭与 `WORK_MODE_IDLE`。

### 判据与自检

不要用"听感"当唯一判据。可量化的检查：

| 检查项 | 正确值 |
|---|---|
| 素材解码的 `c0_errors` | 0（数字采集、未过空口时应无纠错错误） |
| 零射频会话 `relay_units_written` | 等于单元总数 |
| 发射会话模块交帧数 | 与写出单元数同量级 |
| 数据段时长 | 单元数 × 60 毫秒 ± 尾窗 |
| 信道回读第十项 | `off` |

接收方向可以让模块自己报告对端是否在发射，不必靠人掐时间：

```
AT+DMOGETDIGITALRXINFO    空闲回 0,0,0；有信号时回 group,<目标>,<主叫>
```

实测与操作者独立报时吻合（10.06 / 5.10 / 8.06 / 21.04 / 26.29 秒）。

### 容易踩的坑

1. **信道加密开着**——会掩盖其它一切问题，先查这一条。
2. **送已编码的空口帧**——本节的核心，模块会二次编码。
3. **单元长度取 36**——本机是 27，切片会跨单元边界。
4. **按回执节拍供数**——发射态没有回执，会超时拉长时间轴。
5. **服务选项置了加密位**——接收机按加密语音处理。
6. **录音存储是小环形缓冲**——约 70 单元、4.2 秒，整条读一次要一秒多，
   必须只读增量并处理回绕，否则素材会断。

## 一次方法转变的记录（2026-09-18）

这个项目在此之前已经进行了数周。发送方向做到 v0.80，做了大量真机试验，
但始终没有让对端收到可识别的程序音频。2026-09-18 这天换了方法，
在两个多小时内把长期无法定位的缺口收敛到了一个可以单独验证的变量。

把这个过程记下来，不是因为结果，而是因为**为什么之前的方法必然低效**。

### 之前卡在哪里

旧做法是：从主机侧用原始接口重新实现一遍模块的发射会话，改一版、上机试一版。

问题在于这条路径**原厂应用从来不走**。没有任何参考样本可以比对，每一版改动
本质上都是猜测。而项目为了保证证据质量，给每次上机设了很重的流程：
连续三次准入、每次都要新鲜预检、完整原像备份、逐字节恢复核验。
于是一个软件缺陷就被放大成一两个小时的真机仪式，而真正的未知量一次都没被触及。

从 v0.60 到 v0.80 的二十个版本，仅准入环节就成功执行了至少六十次，
每次都通过，每次都没有回答"发射为什么不成立"这个问题。

回头看，症结不是不够努力，而是**观测手段和提问方式都不对**：

- 唯一的判据是对端整机的接收灯与听感，无法区分"没有载波""有载波但帧不合法"
  "帧合法但内容不对"这三种完全不同的情况。
- 每次实验同时受多个未知量影响，失败了也不知道该改哪一个。
- 大量精力花在证明已经成立的东西上，而不是排除尚未成立的假设。

### 这天换了什么

**第一，把固件搬到电脑上跑。**

模块的 MCU 固件早就完整提取出来了（256 KiB，Cortex-M0 架构），
但一直只当作静态反汇编的素材。这天用 Unicorn 把它真正运行了起来
（`tools/emulator/h13_mcu_emu.py`）。

这件事的价值在于：**固件的正确性有客观判据，不是"跑起来就算对"**。
建立过程中固件连续暴露了四个模型缺陷，每一个都是它自己指出来的：

| 现象 | 根因 |
|---|---|
| 停在错误陷阱 | 时钟就绪位被恒置为 1，固件"等待锁相环关闭"的循环永远不满足 |
| 提高时间压缩后跑飞 | 异常压栈做了对齐调整，返回时未还原，栈指针逐次漂移 |
| 重映射后取到错误向量 | 地址 0 未镜像 SRAM |
| 串口初始化一直超时 | 未提供串口使能确认位 |

修正之后，模拟器复现出的启动序列与项目历史记录的板级引脚映射**逐项吻合**：
基带唤醒与复位、锁相环选择、编解码器复位、闪存片选、频率合成器的位串行总线、
以及基带并行总线的片选、方向与选通。这是双向验证——既证明模拟器可信，
也证明那些历史结论是对的。

模拟器还独立重新确认了两个关键地址，并补出了文档里没有的四个。

**第二，直接调用目标函数，而不是等它自然执行。**

模拟器最大的价值不是"能启动"，而是可以任意调用固件内部的任何函数、
任意打桩、记录每一次寄存器读写。遇到需要外部芯片应答才能返回的调用，
就打桩跳过并如实记录——那是替身，不是真实行为，但它让后面的控制流暴露出来。

用这个办法，原厂发射的完整启动序列被完整还原，包括每条命令的确切字节。
这在真机上是做不到的：真机只能看到最终结果，看不到中间的每一步。

**第三，只读旁观真机，不去占用它。**

设备接上后没有停止任何程序、没有占用串口，只是以约 1400 赫兹轮询引脚状态，
然后请设备所有者正常按键发射。

这次观察推翻了一个隐含假设：**真实发射时，那个名为"功放使能"的节点始终是 0**。
与此同时功率表测到 1 到 4 瓦真实输出。两者并不矛盾，结论是该节点根本不反映
发射状态。历史记录里多次把发射后读到的这个 0 与失败并列，据此推断功放没开——
那些判断全部无效。

**第四，让观测能区分竞争解释。**

设备所有者有一台串联接假负载的通过式功率表。这件事改变了验证的可行性：
以前只能问"对端听到了吗"，现在可以先问"有没有射频能量输出"。
后者一眼就能看出来，直接把第一层不确定性消掉。

### 结果

主线缺口从"完全不知道哪里错"收敛到了一个可以单独验证的变量。

最硬的证据来自模块自己的行为，不是手册推断：**模块上报接收到的语音时，
用的是 27 字节；而发送程序一直在用同一个字段发 36 字节。**
27 字节是三个语音帧约 60 毫秒，正是 DMR 一个语音突发的原生长度，
与项目接收链早已确认的结果一致；36 字节是四帧约 80 毫秒，属于另一种制式的单位。

历史上为了凑那个 36 字节，把四个 27 字节接收单元重组成三个 36 字节发送单元。
这个重组方向从一开始就是反的。

修正已实现：三个候选格式各只改一个维度，历史实现保留为默认。离线核验显示，
最接近的那个候选构造出的帧与模块上报接收的帧**只差包类型字节的读写位**。
切分也做了等价性核验：换格式不改变发出去的语音内容，总时长完全相同。

### 可以带走的几条

1. **有固件就把它跑起来。** 静态反汇编看到的是可能性，运行起来看到的是实际控制流。
   一个能任意调用、任意打桩、记录每次读写的模拟器，比几十次真机试验的信息量大。
2. **先找参考样本，再谈实现。** 如果要做的事情原厂设备本身会做，
   就先去看它怎么做；如果原厂不做，要先意识到这一点，别把摸索当成有依据。
3. **观测手段决定实验价值。** 如果两种相反的解释会得到同样的观测结果，
   这个实验就不该做，应该先改进观测。
4. **流程严格不等于方法有效。** 很重的准入流程保证了证据质量，
   却没有保证每次实验能回答问题。二者要分开衡量。
5. **区分路径，别混为一谈。** 这天我自己就犯过一次：把模块内部的内存改写
   和主机侧的协议命令当成了同一条路径，得出了错误结论，随后更正。
   更正保留在提交历史里，不做静默修改。

详细经过见 [开发记录](docs/H13_new.md)。

## 平台概要

- Android 8.1、高通 MSM8909、240×320，公网与专网数字对讲三合一
- 专网部分：独立 MCU（Cortex-M0 类，STM32F0 外设图）经并行主机接口控制基带芯片
- 主机侧经 `/dev/ttyHS0` 与 MCU 文本协议通信，波特率 57600
- 当前模块固件版本 `0.3.66`

## 模拟器用法

```bash
# 启动固件并观察板级初始化
python tools/emulator/h13_mcu_emu.py --flash firmware/mcu/Module_current_0.3.66_full_flash_256k.bin

# 还原发射启动链，汇总所有命令、引脚动作与状态写入
python tools/emulator/trace_tx_chain.py --flash firmware/mcu/Module_current_0.3.66_full_flash_256k.bin
```

模拟器只做模拟与记录，不生成任何可写回设备的制品。

## 边界说明

- 全部工作针对项目所有者自有的设备，用于理解与扩展其功能。
- 文档区分**真机结果、离线验证、静态定位、待验证推断**四个证据层级，不得互相替代。
- 模拟器中凡依赖外部芯片应答的调用均为打桩替身，相关结论不可直接当作设备行为。
