## 三、Android系统与可用应用基础

### 3.1 root、生产应用与按键

- **Magisk 25.2取得root已经成功。** 原厂和修补后的boot镜像均已保存；早期“无root”的状态已过期。启动镜像只适用于对应构建，不可按同平台名称跨机刷写。
- 移动PoC组件和桌面入口已有清理成果。原专网包`com.bozhou.interphone`承担专网业务，不能作为移动PoC残留误删。后期生产基线使用修改版`net.elfradio.h13interphone` v0.7，由其唯一占用`/dev/ttyHS0`。
- `H13KeyRouter` v0.3与Interphone修改版v0.7的三键短长按、松键和互斥已于2026-08-04完成真机验收。物理大PTT为`F1/scanCode 59`，通过显式`com.zello.ui.PttButtonReceiver`及`com.zello.ptt.down/up`控制Zello；小键一、二最终使用`F2/F3`。
- 厂商`.long`事件表示达到长按阈值，**不表示松手**。长按后缺少`.up`，已用前台Activity的`onKeyUp`转包内`M1_RAW_UP/M2_RAW_UP`补齐；不要恢复旧的长按即松键逻辑。
- `content://interphone.settings/state`的`call(STATE_GET)`可读取状态；`STATE_SET`返回空，不能作为有效切频道接口。频道操作应复用Interphone进程内已验证路径，旧的步进广播方案不再作为基础。

可直接继承的实现细节：大PTT由辅助功能服务消费，小键一／二在修改版内分别绑定CH1／CH2；具体频率随频道配置变化，不把最初测试频率固化为硬件限制。生产原包在该基线中为`disabled-user`。修改版已验证开机启动、`START_STICKY`、恢复`single_strategy=private`、重开串口及恢复频道；三个业务组件已有设备空闲白名单。按键只在操作时调前台，不依赖长期霸占前台。

`STATE_GET`返回名称、收发频率、状态和类型；频道变化会`notifyChange()`，可用`ContentObserver`。实际键表是`Generic.kl`，不能按文件名猜用`gpio-keys.kl`，也不能硬编码重启后可能变化的`eventN/deviceId`。小键长按阈值约0.5秒；松键后应用立即请求结束，但模块收尾仍可能使极短点按显示接近1秒，这不是应用固定发射1秒。

**旧`chup/chdown`广播有实测发射副作用。** 在v0.7中曾触发两段短TX，不能用于“无发射切频道”验证。模块重启后还可能先显示内部默认频道，须以生产应用重新下发后的模块确认和状态回读为准。

证据：[H13主记录](H13.md)13.7–13.10、13.20.6；[按键工程](research/h13_key_router/README.md)。“生产基线”指相应历史测试恢复状态，本次未确认今天安装的版本或运行进程。

### 3.2 恢复环境与root制品

原厂recovery实测接受AOSP testkey的整包OTA签名、标准正斜杠ZIP条目，并能运行32位ARM静态ELF；已通过版本的`PT_TLS`对齐为`0x20`。这条已验证的恢复执行链是取得boot及安装Magisk的基础，不是依赖尚未成功的内核漏洞。

有效原厂boot由v4提取器保存到真实VFAT外置卡后取回，大小32 MiB，Android boot header v0、页大小2048；分区为`/dev/block/bootdevice/by-name/boot`。早期仅凭目录可写把文件存进recovery临时文件系统的尝试无效。有效Magisk修补过程完整结束，历史被超时中断的产物不能使用。原镜像、有效修补镜像和恢复包保留在`research/h13_root/`；这不是整机全分区备份或完整刷机验收。证据：H13主记录13.20.4–13.20.6。

### 3.3 Wi-Fi与息屏运行

已定位实际配置为`/data/misc/wifi/WCNSS_qcom_cfg.ini`，vendor位置为链接；相关驱动设置在启动时生效，不能把编辑文件等同于热更新成功。`gEnableDynSplitScan=0`配合STA/P2P静态分配`3/1`取得过约8小时过夜低流量及息屏PTT阳性结果。

原厂文件没有显式`gEnableDynSplitScan=1`，运行值1来自驱动默认值；有效修改是在`END`之前增加`gEnableDynSplitScan=0`，`END`之后内容会被忽略。静态`3/1`未同时改动。过夜样本中远端实际收到语音，松键后Zello在线，但唤醒瞬间仍有无线重试；该瞬间的部分厂家低层日志已轮转，不能用后续扫描日志补称完整捕获。配置备份及两轮证据位于`research/h13_wifi_prima/`。

该结果仅支持“这组条件下初步有效”，没有证明长期彻底消除断流。CPU唤醒锁、TCP保活及其他候选方案不列为已证明的根治方法。证据：H13主记录13.20.7及后续复核。

## 四、硬件控制结构与接口

已建立的基本结构为：Android经`/dev/ttyHS0`访问独立MCU，由MCU控制SCT3258相关专网路径。正常文本协议为57600波特率。固件静态分析支持Cortex-M0／STM32F0架构兼容实现，并已识别3811相关控制、LMX2571及音频编解码控制链；**MCU精确料号及射频芯片的实板丝印仍未确认**。

型号证据应进一步区分：生产代码的`CODEC_SELECT=1`和寄存器序列明确对应**TLV320AIC3204的软件配置**；`3811`控制、Sicomm资料与寄存器行为共同支持**SCT3811直接变频接收器的高置信度识别**，不能简化成“只知道3811三个数字”。这仍未代替实板丝印／走线确认，也不能宣称SCT3811就是CMX994改标。

| Android侧接口或引脚 | 已确认关系及使用边界 |
|---|---|
| `/sys/boptt/audio_switch` | GPIO23 |
| `dmr_switch` | 同时控制GPIO97与GPIO94，不能只记录94 |
| `pa_enable` | 实际为GPIO69，旧GPIO16判断错误；节点名和电平不等于测得RF功率 |
| `ptt_d` | GPIO112，支持`in/out0/out1`；属于模块唤醒AP／UART握手，不是物理大PTT |
| 物理大PTT | GPIO36，低有效，15毫秒消抖，对应`KEY_F1` |
| `ttyHS0`引脚复用 | GPIO20/21、`blsp_uart2`；未据此确定哪根是TX或RX |
| `freq_section=4` | PM8909 MPP4的板级识别分箱；不是RSSI、模块供电或I/Q通道 |

串口必须保持单一所有者。第二个文件描述符曾导致原读取线程收到EOF，不能把“再开一次串口”作为无侵入旁路监听。

Android侧存在AUXPCM时钟或已注册DAI，不能证明它物理接到专网模块。已测公开无主机音频节点未得到有效帧；Android内置麦克风`tinycap`阳性只证明Android录音链。现有结果既没有打通模块数字PCM，也没有穷尽否定所有潜在板级路由。

证据：H13主记录14.1–14.3、14.2.2及后续音频路由记录。

### 4.1 MCU侧已经恢复的总线分工

下表主要来自0.3.54固件的完整控制时序及手册交叉核对；PC10、PC6、PC13等另有0.3.66定位。它描述MCU的软件引脚角色；未做导通确认的外部焊点不视为实板测量结果。

| 路径 | 已恢复映射／行为 | 证据层级 |
|---|---|---|
| SCT HPI数据与控制 | PD0–PD7为数据；PA11为片选；PA12为读写方向；PF6为数据选通 | 静态时序与手册一致，采用Motorola模式，非Intel模式 |
| SCT复位与唤醒 | PC11为硬复位；PC12为NMI路径；PA8的脉冲与INT0唤醒匹配 | 前两项有明确控制路径；PA8外部连接为高置信度映射 |
| SCT状态与时隙 | PC10读取HOBIB；PC6为双边沿输入，与PIO3／RF_TIMING匹配 | PC6外部芯片管脚仍有物理确认边界；不能把PC6当INT0 |
| 射频门控 | PC13为RF开关控制；PF3低有效TX／PA门；PE6在RX为高、TX／休眠为低 | MCU控制行为已定位；PE6实际供电终点未确认，不直接命名为SCT3811的RXEN |
| 其他控制 | PE5为codec复位；PC4控制TX VCO供电；PA1控制LMX2571 CE | 静态路径；外部实体连接仍以实板为准 |
| LMX2571 | PC1片选、PC14时钟、PF10数据输出、PC0读回 | GPIO模拟串行总线，不占用SPI1 |
| SPI NAND | PE12片选；PE13/14/15为SPI1时钟／MISO／MOSI | 命令集、初始化和录放调用链支持，不是codec或合成器总线 |
| 外部EEPROM | PC15为软件I²C时钟、PE3为数据，16位字地址 | 型号和容量未确认；不是射频芯片使能线 |
| AP握手 | MCU PD8与AP GPIO112／`ptt_d`的方向及脉冲相符 | 高置信度板级关联，未用导通测试确认 |

PB4与SCT的`PLLBYPASS`、PB3与`PLLSEL2`有静态及手册对应证据，后者仍包含固定电平推断。隐藏`pllctrl`实际上切换MCU系统时钟源并重建串口／定时器，不能当作LMX2571命令。MCU DAC属于功率／偏置控制，不承载语音或I/Q波形。

### 4.2 外部音频芯片与接收前端

TLV寄存器可由SCT通过HPI `TYPE=0x40`转发访问，不能在MCU中找不到硬件I²C/I²S初始化就否定该链。已恢复的生产初始化含右DAC的Biquad A系数及双缓冲切换；按24 kHz假设复算为轻微低频衰减／高频补偿，不是语音低通或完整FM预加重验收。工具为`research/h13_radio/analyze_tlv320_filter.py`。

SCT3811相关控制通过`SPI_OPERATION(0x6d)`由SCT代管。十进制寄存器17/18/19/21/23分别与CMX994的`$11/$12/$13/$15/$17`兼容定义对应；校准记录名`3811Reg17`中的17是**十六进制$17**，对应I/Q直流偏置，不是十进制17或频率寄存器。`$11=0x42`与参考器件偏置使能语义仍有差异，不能把全部CMX994位定义无条件套到H13。

资料与固件支持“模拟I/Q→外部codec→SCT”的窄带接收架构推断，但H13的实际串行采样率、左右映射及可读I/Q出口未测通；参考机型原理图不是H13原理图。证据：H13主记录14.6.1–14.6.3、14.6.9–14.6.12。

### 4.3 原应用与MAX11工具的可复用接口

官方MAX11写频工具已归档，其实现使用ADB文件传输、属性和广播，不是另一个私有USB写频协议。原应用`INI_READ`曾实测生成`/sdcard/configuration.txt`；历史配置含DMR与模拟频道，选择模拟频道后界面切换、模块返回`+DMOSETANALOGCH:0`，随后成功恢复。**模拟功能没有被删除**，但该无发射切换本身不是FM程序音频注入或完整FM空口验收。

已实测的文本查询包括模块连接／版本、数字／模拟频道、`DMOGETRSSI`、`DMOGETDIGITALRXINFO`和`DMOGETMESGINFO`。RSSI返回顺序为窄带、宽带；空闲状态零值不等于业务接收已验证。状态Provider只是原应用接口；是否可供其他修改版使用须核对其实际authority。

静态代码已定位`DMOSENDMESG`的二进制内容、`group/IPconfirmation/IPnonconfirmation`类型及`DMOAUTOUPDATAMESGINFO`接收解析；这提供数据业务开发入口，最大净载荷、分片、重试及端到端遥控均未验收。CSBK的Radio Check或私有激活／停用状态机不能直接当任意控制数据通道。证据：H13主记录14.4.3–14.4.4、16.5.1。

## 五、已经取得的固件与地址基础

### 5.1 固件层次必须分清

1. **MCU完整Flash：** `0x08000000..0x0803ffff`，262144字节，历史双遍读取一致。
2. **当前MCU应用：** `0x08006000..0x0802edeb`，167404字节，对应模块0.3.66。旧0.3.54地址不能直接移植。
3. **MCU驻留引导程序：** `0x08000000..0x08005fff`，24576字节。历史文件`SCT3258_resident_bootloader_current.bin`名称容易误导，内容属于MCU引导区，不是SCT3258完整DSP程序。
4. **应用内嵌SCT加载器：** 当前地址`0x0802cb8a`，2048字节，与旧加载器一致。这不等于DSP完整固件已经读出。
5. **SCT3258内部固件：** 完整Flash提取、`coded1/2/3`解码仍未完成。公开SCT3288的`abc`与异或`0x76`仅解释外层容器；跨角色相同地址不构成同明文配对，旧拟合不能当解密成果。

当前初始化解压器已恢复980字节数据到`0x200000c0`，BSS范围为`0x20000494..0x200056e7`。Cortex-M0通过SRAM重映射使用48字的向量表，不能套用Cortex-M3/M4的`VTOR`操作。线性反汇编会把数据误作指令，后续分析须核对实际控制流。

静态分析还恢复了24xx兼容、16位地址的外部EEPROM访问协议，以及412字节射频校准记录、48字节基础参数记录的布局；确切型号和容量未确认。整片Flash的`0x08005000..0x0800500f`有16字节非空内容，**用途尚未由当前固件调用链确认**，不能写成已经确定的授权、配置、密钥或校准区；作为潜在设备唯一数据保护，不复制原字节，也不当可清空空间。

证据：H13主记录14.4及14.10.15–14.10.18。固件提取成果指MCU层，不能简称为“整套射频固件已破解”。

### 5.3 模块升级接口与公开DSP容器

`/system/bin/dmr_upgrade`已经提取并静态还原：升级分支会先改变握手GPIO并复位模块，再以57600、8N1使用YMODEM传输；固定对端文件名`USTB_V3_1.Bin`不是已证明的H13版本名。数据块使用128／1024字节载荷，CRC多项式`0x1021`、初值0；不能误套CRC初值`0xffff`。部分错误分支缺少正常GPIO恢复。**`-s/--status`并非只读查询：它打开`/dev/ttyHSL1`并发送ASCII `A`，不读取模块状态。** 本成果是静态协议恢复，没有执行未知模块固件升级。

厂商工具中的2 KiB基础加载器与H13内嵌块逐字相同；`mode0`为基础／User Flash启动，`mode1`为User2 Flash，`mode2`为DMR System Flash，不能把`mode1`叫作HPI维护加载器。真正HPI变体另有确定的补丁差异，见`research/h13_radio/public_sct3258/extracted_loaders/`。

公开07BF HEX的六个运行区、293920字节已完整解析为198条下载命令，并重建六份`.dat`等价容器，逐字节往返一致。两个完整应用角色为User Application和Modem2，其余四个为vocoder子应用；子应用没有伪造未知入口。**这是公开固件容器成果，不是H13实机DSP读取，也不是coded载荷解密。** 工具入口为`analyze_sct3258_hex.py`、`index_sct3258_download_stream.py`、`reconstruct_sct3258_dat.py`；已撤回的跨角色coded配对不得作为解码训练依据。

证据：H13主记录14.7、17.9、17.25、17.99–18.00；[加载器提取清单](research/h13_radio/public_sct3258/extracted_loaders/README.md)、[容器重建清单](research/h13_radio/public_alinco_sct3258_archives_20260807/analysis_20260807/reconstructed_dat_20260807_082946/manifest.json)、[coded配对纠正](research/h13_radio/analysis/2026-08-09-sct3258-coded-equivalence-correction.md)。

### 5.4 SCT指令与加载器静态分析的可复用部分

公开未编码加载器、BootLED及示例程序已形成指令字段、控制流图和数据流审计工具，保存在`research/h13_radio/tools/`及`research/h13_radio/public_sct3258/analysis_20260809/`。可继承的是受样本约束的部分模型，不能称为完整SCT反汇编器：

- 分支候选为高半字节`0/4`、条件半字节及有符号8位字位移，目标为当前字地址加1再加位移；还须过滤数据区和不成立的控制流。旧模型混入的`84/C4`边已撤回。
- `2/3`类分别装入低／高字节；`A`类的结果字段与两个输入字段、`6/7`类的写／读和`[数据字段][无符号偏移][基址字段]`布局有跨程序静态支持。正式助记符、完整指令语义仍未恢复。
- `0xF272`是紧凑寄存器块的**候选基址**；带偏移的访问不能全称为访问同一个FIFO。`0xF27C`与部分复制链有关，但尚不能命名为已确认的HPI接收、发送或状态寄存器。

证据：[指令字段纠正](research/h13_radio/analysis/2026-08-09-sct3258-nibble-isa-and-literal-boundary.md)、[跨程序数据流](research/h13_radio/analysis/2026-08-09-sct3258-register-memory-and-f272-endpoint.md)、[地址偏移纠正](research/h13_radio/analysis/2026-08-09-sct3258-memory-offset-and-f272-register-block.md)。这些约束可避免重做已完成的静态定位，不构成加载器改写或Flash访问验收。

## 六、DMR接收：已经可用的是哪条链

正常Interphone路径下，H13与TYT的DMR双向通话已有用户确认。早期单向现象最终与双方TG不一致有关，不能继续据此认定私有制式或H13接收硬件故障。

已验收的程序可读音频链为（这里指自然RX磁带样本，不泛指所有同长度HPI数据）：

`DMR接收 → 27字节CHAN_D → 三个9字节AMBE信道帧 → 软件解码 → 8 kHz、16位有符号PCM`

- 每个9字节AMBE帧约对应20毫秒、160个PCM采样；一个27字节单元约60毫秒。已确认的位序是标准DMR空口交织，使用`air/forward/msb/normal`，不是连续49位私有打包。
- 旧探针v0.90取得244个单元、6588字节，即732个AMBE帧；经`chan_d_to_wav.c`／`mbelib`解码得到14.64秒音频，用户确认清晰人声。这是可信的接收内容阳性样本。
- 较早分块读取仍有缺口：v0.17的201单元流至少丢360毫秒；v0.18补回尾单元后仍至少丢300毫秒。不能将现有捕获称为长期连续、无缝或零丢帧接收。
- RSSI探针已自主捕获接收开始／结束及录音块，宽带RSSI随接收变化；窄带读数曾固定在−137。尚无标定依据，不直接显示为可信dBm。
- 模块原应用录音存于模块NAND，Android普通接口取得的录音元数据和回放索引，不等于导出的音频载荷。

原应用的`DMOSETRECORDSW`、`DMOAUTOUPDATARECORDINFO`和`DMOSETPLAY`分别负责模块录音、索引上报与模块内回放。历史一个连续呼叫被拆成最多72个单元／4.32秒的录音块；UI出现多条录音不能直接解释为现场音频中断。模块配置中的发送目标组和接收组列表是两个字段；历史修改接收列表和RX时隙未解决那次单向问题，最终TG纠正后才获双向确认，不把旧排查候选写成通用修复规则。

**直接硬件PCM必须单独定性。** 已观察到HPI `type=0x30`、`count=160`、`LENGTH=323`的流，多数线上帧为328字节，另有330字节样本；历史恢复器从328字节帧提取318个偶数字节并补样，不能说每帧已无损取得160个真实采样。受控讲话样本752帧中741帧RMS小于30，未形成可辨语音。WAV封装正确、20毫秒周期和三帧对齐60毫秒，只证明容器与速率，不能证明内容来自DMR解码器。

因此，模块自身解码到扬声器可用；**Android可读的硬件直出接收PCM尚未打通**。早期主记录、封存说明及9月16日简要交接中泛称“已确认硬件解码PCM”的句子，均应按此收窄。决定性来源：H13主记录18.58–18.60，以及[直接PCM纠正报告](research/h13_radio/captures/2026-08-08/p1p2-redo-corrective/CORRECTIVE_P1_P2_REPORT.md)。

## 七、串口、HPI与恢复框架

已证明57600→230400→57600的文本面可逆切换；判据包括标记、原向量恢复、模块连接与版本响应，以及临时SRAM原像恢复。原始桥在230400下的进入／退出生命周期也已有证据，不能把它扩大为连续PCM或任意HPI业务已成功。

- `0x08010a00(r0=baud)`只有在桥标志为零时接受目标速率；桥标志非零时强制115200。因此目标速率必须在入桥前设置并验证，不能入桥后再次调用而仍假定230400。
- 已接受的56字节一次性桩将被中断的寄存器和异常返回令牌`EXC_RETURN`保存在栈上，保持8字节对齐，调用后恢复向量并回到原处理程序。48字节旧桩未正确保存该令牌，52字节旧桩用会被被调函数清零的`r2`保存，均禁止复用；`r0–r3`本来就是调用者保存寄存器。
- 隐藏内存读取依赖`print 1`；读取及恢复核验结束后才能关闭调试输出。成功打开串口或执行写函数，均不能替代独立模块应答。
- 当前原始桥的HPI头为`84 a9 61 + 两字节大端正文长度 + packet type`，共6字节，正文从偏移6开始；奇数总长度的发送帧追加一个不计入`LENGTH`的`00`补位。36字节载荷在相应数据帧偏移8，1280字节`SPEECH_SAMPLES`载荷在偏移9；不能混用payload与正文起点。判断必须包含完整帧、请求后的响应窗口及会话状态。事件`0x7f`为`DMR_SLOT_FOUND`，不是任意控制噪声。
- `HOBIB`位于MCU PC10，高电平表示`hibf OR hobe`，不能简化为单一“可写／就绪”信号。
- 8 kHz、16位连续PCM超出57600串口容量；软件AMBE的44字节`data36`请求每80毫秒一包，在57600具有足够名义带宽。两种载荷不能沿用同一个带宽结论。
- 自动退桥、真实SRAM备份与逐字恢复、文本面重连及归还生产端口的框架可复用。动态队列必须在稳定条件下取得真实原像，不能用全零或猜测值恢复。

恢复范围须按字段区分：`0x20000134..0x20000137`是PC6动态边沿累计计数，后期已纠正为只观察、不写回；不能把它与`0x20000138..0x2000013f`稳定控制字段整块恢复并要求逐字相等。所有需要恢复的稳定字段仍须真实原像及恢复后回读。`print 0`必须晚于最后一次隐藏内存恢复核验。证据：H13主记录2026-08-21的v0.16／v0.17纠正条目。

56字节桩的冻结哈希、完整验证阶梯和具体制品见H13主记录18.27；不能仅按字节长度选择桩。此处保留机制，不复制历史安装、停应用或写内存命令。

可复用的低层事实还包括：普通文本UART接收环为`0x20000504`起2000字节，命令复制缓冲为`0x2000132c`起、上限1200字节；桥标志非零时绕过文本环，USART接收按字节调用HPI写包装。发现静态丢唤醒竞态不等于证明某次loader失败由它引起，512次快速只读链曾全部正常而未命中竞态。

`0x080105c8`是有超时的同步忙等接收器，不是异步完成回调；窗口内后帧可覆盖前帧输出槽，不能拿最后一个槽代替完整帧带。`PENDING`来自探针哨兵，不是固件返回码；返回`-2`也不能单独解释为整个窗口从未收到帧。软件tick须按实际时基换算，历史波特率基线约100 Hz，不能把tick数直接当毫秒。结构化事务、配置批处理、原始桥泵送的已知路径不同；未找到某个立即数不等于全局排除其他提交路径。证据：H13主记录17.41、18.10、18.28、18.280；[同步接收器复核](research/h13_radio/analysis/2026-08-17-step6-hpi-static/080105c8-完成路径.md)。

## 八、软件AMBE发送编码与无射频基线

### 8.1 编码器已经运行成功

发送端采用`C:\Dev\usrp-test\plan_b`的`src/ambe_ffi.rs::AmbeEncoder::encode()`及底层`imbe_vocoder`、`mbelib`、`ambe`实现；项目已有[源码快照](research/software_ambe/source_snapshot_20260818/)。`ambe_tones.rs`的启发式音调字节不能替代真实编码器。

旧探针v3.71完成32位ARM／JNI无射频实机验证：每160个8 kHz、16位有符号采样产生一个9字节AMBE帧。静音52帧、800赫兹52帧、SOS 104帧与桌面冻结输出逐字一致；记录中的串口打开、射频命令和频道修改次数均为零。

1000次单帧编码耗时为：P50 **2.868333毫秒**，P95 **3.236198毫秒**，P99 **4.775938毫秒**，最大 **12.990885毫秒**。这证明该次有限样本的计算性能，不能据此保证任意负载下长期20毫秒实时零丢帧；预编码供数与实时采集编码应分别验收。

后期软件调用合同也必须保留：`MBEEncoder::encode()`的调用方工作区至少为72字节，不能因最终输出是9字节而只分配9字节；v0.45已因此栈越界。mbelib内部已推进的状态不能再重复推进。跨Windows／Android的软件合成包含平台`rand()`随机相位，不能将PCM逐样本相等作为通用验收门；冻结AMBE／49位参数仍可逐字比较，PCM应采用有依据的内容、频谱和包络门。v0.51重新使用与v3.71逐字相同的冻结PCM后通过软件闭环，不能把“同为800赫兹但重新生成的不同PCM”视为输入未变。来源：射频主账45.10–45.24。

独立Golay、位序与回编核对已证明`encode_dmr()`输出是标准72位DMR信道码字，摩尔斯104帧全部可回编一致。自然接收732帧的冻结差异轮廓为总Hamming距离1521、最大4、29帧逐字相等；不能像软件自产向量一样要求全零距离。旧记录将其称为接收残留误码，但这些统计本身不足以定位差异究竟形成于空口还是模块处理。末字节高半字节全零只是该磁带样本特征，不能拿它否定软件格式。

历史“方言A”自然RX磁带、“方言B”external实时回送和裸49位装箱必须分开：后两者在该72位映射下不是干净码字，收到信用也不能证明其内容正确。不能将第六节自然RX的格式结论外推到所有27字节回送数据。

证据：[v3.71结果及向量](research/software_ambe/captures/2026-08-18/v371-h13-software-ambe-no-rf-20260818_133705/device_raw/software_ambe_no_rf_20260818_133705/)、[射频主账](rf_test.md)第18节及第43–45节纠正。

### 8.2 数据转换与privacy的已校正实现

当前源码实现为：先从明文72位信道帧恢复49位语音参数，执行privacy处理，再进行Golay／白化／交织，最后在72位物理位置集合`{21,67,69,71}`写入C3（具体位序由冻结实现定义，不按集合顺序重写）。不能对已经完成信道编码的成品直接做“前49位异或”，也不能把C3误写成49位参数中的连续四位。

privacy／MI状态按连续帧和18帧超帧推进，不在每个36字节包边界重新初始化。当前49位往返只豁免未保护的原始位47、48，原始位23应由Golay恢复；信道往返检查另豁免上述四个物理位置，不能使用早期更宽的豁免规则。运行参数应来自相应会话的真实14字节快照，旧测试夹具不是未来设备的凭证。桥接绕过MCU正常privacy处理链，信令声明和正文处理必须相符；预检结束要恢复并回读privacy-off。

三个9字节帧组成27字节接收单元；四个9字节帧组成36字节供数单元。四个27字节重组为三个36字节只是保持顺序的字节等价，**不能独自证明模块发送入口的超帧语义和空口可听性**。`data36`请求为`84 a9 61 00 26 03 01 24`加36字节正文，共44字节。

源码入口：[SoftwareDmrPrivacyPipeline.java](research/h13_dmr_tx_harness/app/src/main/java/net/elfradio/h13dmrtx/SoftwareDmrPrivacyPipeline.java)、[DmrPrivacy.java](research/h13_dmr_tx_harness/app/src/main/java/net/elfradio/h13dmrtx/DmrPrivacy.java)。这些实现已有离线及无射频验证，尚无最终空口内容验收。

**尚未闭合的是H13发送入口实际要求的内容语义。** 上述软件分层、独立自然RX阳性对照和短信用，都不能单独证明模块在该External DMR状态下期望的49／72位表示、privacy声明、C3相位与主机输出完全相符。当前流水线是已验证可复现的软件候选，不能命名为已获H13空口验证的唯一TX格式。

## 九、硬件编码器封存与射频发送停点

### 9.1 内置PCM→AMBE分支

内置硬件发送编码的新增真机研究封存于**旧探针v3.70**。已保留的成果包括四条桥前控制确认、1290字节PCM完整进入适配器、部分样本中安全线程与原固件读写函数返回，以及5044字节真实SRAM原像恢复框架。

v3.70的决定性结果为`rx_len=1290`、`hpi_attempted=0`、`hpi_completed=0`、线程入口计数0：该次没有命中安全线程窗口，不能解释为声码器运行后编码失败。可归因的新AMBE输出、连续消费及内容因果对照均未验收，状态固定为**成果封存、验收未完成**。此前证据缺失或被污染的样本不能用于稳定性计数。

v3.71以后的软件AMBE工作是另一条分支，不能因版本号增加就认定硬件封存已经解除。冻结依据见H13主记录的2026-08-18封存条目及[项目规则](AGENTS.md)。

### 9.2 最新RF结果：v0.80未形成TYT可接收信号

历史上独立发送程序v0.7曾让TYT听到十余秒连续噪音，设备记录的RF窗口为13966毫秒。这是接收侧阳性对照，证明历史控制组合曾产生对端可接收的射频表现；内容不可识别、原会话恢复又未闭合，仍不是成功发送基线。该样本与v0.80必须分开保存，不能因后者无接收就抹去前者。原件见[早期RF阳性捕获](research/h13_radio/captures/2026-08-20/new-dmr-tx-harness-low_power_rf-20260820_205031/)，H13主记录2026-08-20 21:48补录。

中间里程碑也不能丢弃：v0.41完成五包五信用、HPI收尾、RF关闭与生产恢复，但TYT只有约1秒机械噪音；这是控制／恢复基线，不是内容阳性。v0.72射频样本仅有约0.5秒异常声音、24个PC6周期；v0.73确实增加6240毫秒播放窗，记录127个PC6周期，TYT约5秒断续接收及短咔声，仍无可识别音频。这证明增加播放窗产生了可观测变化，同时否定“只补播放时间即可成功”。来源：射频主账第43节、45.214、45.230–45.233。

计数与时间不能混读：v0.72的SysTick保持计数位于`0x20003074`，PC6低沿计数位于`0x2000013a`；后者的160不是已证实的16秒定时器。最终读到剩余计数和`ROF!`，不能倒推出RF何时关断。v0.73的`memread`已内置三次重试，旧“没有重试”的裁定后来撤回；真实缺陷包括失败尝试未逐次落盘、非关键全量后态读取阻断恢复。不得按旧误诊再次增加盲重试。

独立发送程序v0.80在2026-08-24确实写出了五setup、五VLC、78包、终止与清理请求；正文首末写出间隔6160毫秒。用户确认TYT无接收灯、无载波表现、无声音。**不能描述为“语音已经发射，只是TYT解码失败”。**

软件开始标记、`ROF!`关断标记及约120个PC6周期只是内部控制证据。静态复核发现复用的`v009_slot_gate`只操作部分GPIO、计数和标志，缺少完整生产RF配置调用。生产链`0x08015c7c → 0x08019480 → 0x08024dc0`及返回后的控制流，是已定位的分析缺口；它仍是有证据支持的优先方向，**不是已经证明的唯一根因或修复方案**。

该次随后文本面无响应，未生成最终原子结果，也未完成原会话恢复证明。已抢救4526个文件、1217727字节；设备侧截止器完成模块硬关闭，之后USB重启并重建生产基线。重启后的恢复不能补算原会话成功，v0.80不能作为可执行成功基线。

证据：H13主记录18.294、射频主账45.295–45.296；[v0.80失败捕获](research/h13_radio/captures/2026-08-24/new-dmr-tx-harness-realtime_relay_software_privacy_triple_sos_low_power_rf-20260824_233335/)、[重枚举后恢复核验](research/h13_radio/captures/2026-08-24/h13-usb-recovery-v080-post-reenumeration-20260824_235025/)。

### 9.3 功率与FM的有效边界

静态分析已定位功率控制链：频道高／低档选择`0x20004204`运行校准表中的`+0x18/+0x58`，按最近频率锚点取值而非插值，经`0x20002de6`的16位值、PC6时隙回调`0x08010fc0`到DAC包装`0x0800e098`。高沿调用的`0x0800e6e8`写GPIOC的BSRR bit13，即PC13；原记录18.102中的“GPIOB ODR”是笔误，本次按冻结镜像字节核正。这是控制路径成果，DAC码尚未标定为毫瓦；低功率档也不等于毫瓦级。

`0x0801ff34`与仅拉低PE6的`0x0801ff4a`不是等价的RF关闭路径。FM VoiceIn旧探针v1.20曾完成五次codec确认、五个1280字节PCM块及五条信用、终止和恢复，但用户未听到TYT音频；同版本另一尝试在首条codec确认就失败，未进入PCM阶段。成功样本的136字节响应原件按控制／数据分别拼接，文件顺序不等于线上时序。FM可识别程序音频仍未验收，不能把信用成功称为稳定射频成功。证据：H13主记录18.102–18.103、18.184及[8月9日交接](H13_reverse_engineering_handoff_2026-08-09.md)第四节。

## 十、蓝牙SCO与跨应用音频

- v1.0探针取得耳麦的16 kHz、16位单声道PCM，用户听辨确认，证明H13的HFP、AudioPolicy和HAL支持SCO输入。
- v2.0仅用前台服务维持SCO，不自行录音；未修改的系统录音机仍使用普通`MIC`音源，HAL实际进入`audio-record bt-sco-wb`，跨应用蓝牙输入成立。仅配对或连接A2DP不会自动产生这一效果。
- v2.1的10秒健康窗口没有重复改写音频模式；停止后恢复`MODE_NORMAL`、`FOR_RECORD=FORCE_NONE`、无活动SCO且服务退出。该次验证的是保持与恢复，不是重做所有应用录音。
- v2.2修复标题显示并确认安装身份，服务逻辑继承v2.1。最终制品可作手动可逆开关；没有把长期自动保持SCO设为默认，因为媒体质量及功耗存在取舍。

Zello实际发送、原厂专网应用从蓝牙取音、蓝牙到射频模块均未验收，不能由系统录音机阳性外推。证据：H13主记录18.295–18.297；[直接耳麦录音捕获](research/h13_radio/captures/2026-08-26/bt-sco-mic-proof-20260826_194308/)、[跨应用与恢复捕获](research/h13_audio_routing/captures/2026-08-26/)。本文不嵌入个人录音或其中内容。
