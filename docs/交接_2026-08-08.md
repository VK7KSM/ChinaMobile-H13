## 4. Established Platform and Safety Baseline

- Android: 8.1 Qualcomm platform; bootloader unlocked and device rooted for
  authorized local research.
- Radio path: Android application -> `/dev/ttyHS0` -> MCU text/HPI face ->
  SCT3258 radio/DSP -> board RF/audio path. The SCT is not directly attached to
  Android as a general SDR sample device.
- Production Interphone normally owns `/dev/ttyHS0`. A Probe must only disable
  the specific owner during the bounded test and then restore it.
- Normal MCU text protocol: 57,600 baud.
- The safe 57,600 -> 230,400 -> 57,600 text round trip is proven. It proves
  the MCU text face only. Raw bridge operation and a subsequent audio/RF result
  are separate gates.
- `0x08010A00(r0=baud)` only honors the supplied rate while bridge flag
  `0x2000015C` is zero; otherwise it forces 115,200. Change baud before raw
  bridge entry, never after setting that flag unless 115,200 is intentional.

### Non-negotiable SRAM/exception rules

- The failed 48-byte v0.63-v0.65 and 52-byte v0.66-v0.67 SysTick stubs are
  permanently forbidden. They lost `EXC_RETURN` by retaining it in caller-
  saved registers across a call.
- Only the documented 56-byte stack-safe v0.68+ stubs may be used. Their full
  hashes are in `H13.md` section 18.27.
- Before an SRAM adapter is armed, read the bridge flag, original SysTick
  vector, temporary window and target bytes; upload in words; read back the
  full region; verify the exact hash; then arm. Restore and verify after use.
- If baud or MCU text state becomes uncertain, preserve logs and use the
  documented recovery/reboot route. Do not send speculative commands.

## 5. Confirmed Receive Data Planes and Their Limits

### 5.1 DMR `CHAN_D`

This is a real and useful result:

- Live DMR reception yielded complete 27-byte `CHAN_D` units.
- One unit contains three 9-byte AMBE blocks and represents approximately
  60 ms of DMR voice.
- The matching `0x7F` SCT event is `DMR_SLOT_FOUND`, not arbitrary control
  noise.
- The exact 27-byte units can be preserved, analyzed and sent to a suitable
  AMBE decoder. The owner confirmed intelligible decoded voice from that route
  (see `H13.md` sections 18.57-18.60).

### 5.2 Claimed direct RX PCM must be described carefully

Earlier captures contain framed `type=0x30, field=0x00, length=160` records,
and the wire parsing was improved from a false 330-byte stride to the observed
328-byte stream cadence. This establishes framing and a candidate 160-sample,
8 kHz signed-16-bit representation. Three 20 ms frames align numerically with
one 27-byte/60 ms DMR unit.

It does **not** establish a usable SCT/board "chip direct RX PCM" product:

- P2's framed samples did not decode to recognizable received human speech.
- The same RF session's `CHAN_D -> AMBE` route did yield intelligible speech.
- Subsequent `PROCESS_MODE`/Voice OUT and local decoder-route experiments did
  not turn the type-30 content into intelligible RX speech.
- Static audits did not find a proven HPI or AT-level linear-RX-PCM export.

The current evidence-based conclusion is therefore: the transport framing was
observed, but an intelligible, controllable, chip-direct RX PCM export remains
unproven. It may be unavailable without a different undocumented DSP route or
hardware access. Do not regress to calling P2 "RX PCM solved." Read sections
18.57-18.63 and 18.86-18.93 before proposing more PCM tests.

### 5.3 I/Q boundary

No raw RF I/Q source, baseband sample rate, HPI I/Q command, DMA endpoint or
board route has been demonstrated. Software access to the MCU/SCT protocol does
not prove access to internal DSP I/Q buffers. Without a new documented route or
physical hardware modification, wideband SDR and arbitrary RF modulation are
unproven and must not be promised.

## 7. Current External Encoded DMR TX Findings

### 7.1 What is positively proven

1. `VOCODER_IO_SET(0x60)` was accepted by the actual H13 SCT application in
   the v1.05 no-RF test. The isolated response was `... 3e 00`, not `17 06`.
   Evidence: `H13.md` section 18.106 and its capture directory.
2. This proves route acceptance only. It does not prove a call session,
   36-byte credit, data consumption, PTT, RF transmission, RF power or audio.
3. The MCU raw-HPI field-1 parser at `0x0801A860` sends field-1 bodies to
   `0x0802680C`. Its 36-byte branch copies a full 36-byte body and reaches
   `0x0801D770`, which can call the generic packet sender `0x0801B300` with
   `4 * 9 = 36` bytes. This is a genuine host-to-SCT forwarding path.
4. The known native H13 DMR route is a different 27-byte path: four slots of
   `flag + 27 bytes`, followed by a separate zero-length/credit consumer that
   sends 27 bytes. Its logic and state gates are distinct from the immediate
   field-1 36-byte forwarding branch.

### 7.2 What is explicitly not proven

- The 36-byte branch has not been tied to a `0x60` DMR call session.
- It has not yielded a vendor credit or a valid external-encoded data unit on
  this H13 application.
- It has not emitted RF and must not be tested by feeding invented 36-byte
  content.
- A captured 27-byte `CHAN_D` must never be padded or arbitrarily transformed
  into a 36-byte unit.
- Profile values selecting 3 or 4 units have not been named as DMR/dPMR or
  assigned to a `VOCODER_IO` value without further proof.

### 7.3 Current static state-machine map

- `0x20000410 == 1`: native 27-byte ring/credit service state, set only when
  active profile `+30` is nonzero. It is not a generic PTT boolean.
- `0x20000410 == 2`: a different host field-forwarding session state. Do not
  call it just "PTT" or use native credit semantics for it.
- `0x08024DC0` is the key configuration routine that establishes the native
  ring state under profile `+30`; `0x08015C7C` is one configuration wrapper.
- `0x0801F344` only logs `DMOPTT:0`/`DMOPTT:1`. `0x0801FE18` only logs module
  state names such as `RxStart`/`TxStart`. Both were previously misleading
  candidates and are **not** SCT call-control functions.
- `0x08018320` clears and materializes a 40-byte session record at
  `0x200019A8` and changes state at `0x20000160`. It does not send an SCT
  packet or access GPIO/PTT/DAC. `0x08015C7C` calls it but also has no direct
  call to generic sender `0x0801B300`.
- The most likely remaining model is that a later state-machine/task consumes
  the session record asynchronously and then issues actual SCT control. This
  is a supported inference, not proven fact.

Relevant detailed evidence: `H13.md` sections 18.104-18.111.

## 8. RF Power Findings and Boundary

- The early attribution of `0x0801D908`, `0x0801D938` and `0x0800DE64` to
  power control was wrong. Do not repeat it.
- The real current DAC wrapper candidate is `0x0800E098`, initialized through
  DAC1 base `0x40007400` at `0x0800E060`.
- A PC6/SCT `PIO3/RF_TIMING` edge callback at `0x08010FC0` reads a 16-bit code
  from `0x20002DDC+10`, applies it through the DAC wrapper, and later writes
  zero on the matching timing/termination path. This is strong evidence that
  the field participates in the RF timing/power-bias chain.
- It is not a calibrated milliwatt value. The runtime producer of the field,
  exact low/high selection and antenna-output mapping remain to be closed.
- Any RF test requires prior explicit owner permission plus external calibrated
  measurement before asserting an upper power limit.

See `H13.md` sections 18.101-18.103.

## 10. Gateway / Radio OS Boundary


That code is reference material for network-side DMR/AMBE handling. It is not

machine for user PTT, BM call start/data/end, RF busy/conflict handling, RF
TOT, forced release, disconnect and reboot recovery.

The practical product route remains:

1. first, a DMR/BM and FM voice gateway using proven audio/AMBE boundaries;
2. then a native external-encoded RF TX path if Milestones S1-S3/D1-D2 prove
   it; and
3. only later, any MMDVM-style RF modem claims. A DMR audio gateway is not the
   same thing as a complete MMDVM RF modem.
