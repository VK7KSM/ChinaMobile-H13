# 模拟 FM 接收音频无法经 HPI 进出 H13 模块 —— 离线三层判定

- 日期：2026-10-15（悉尼）
- 编写：H13-dev2
- 性质：纯离线、只读判定（厂商工具反编译源 + SCT3258 数据手册 + 固件反汇编/Unicorn 模拟器实跑）。未碰真机、未发射、未改任何设备现场。
- 适用：H13（SCT3258 基带 DSP + Cortex-M0 MCU，模块固件 0.3.66 / `V2.01.07I3`）。供 Radio OS 平台规划引用。

## 结论先行

- **把模拟 FM 的解调接收音频经 HPI 导出给 MCU/Android：【已证不可行】**（按出厂固件与公开文档）。模块不会把模拟 FM 解调音频以 PCM 形式经 HPI 吐出。
- 残留的「强行改路由让它吐出来」的可能性：**【推断不可行】**；可用一次真机无射频实验彻底关闭（见末节），但三层证据已足够强，该实验仅为确认性。
- **镜像结论（发射侧）**：模拟模式下经 HPI 注入 PCM 只得未调制载波（CW），同根原因。
- **数字侧不受影响**：DMR 的接收 PCM / CHAN_D 经 HPI 导出【已证可行】（走声码器域，能路由到 HPI）。

一句话根因：**H13 在架构上是一台「自足」的模拟电台——模拟 FM 的收/发音频完全锁在 codec 内部模拟链（右 ADC=FM 解调 → DSP → 左 DAC=扬声器；麦克风=左 ADC → 调制器/VCO），而 HPI 这条能通到 Android 的路只服务数字（声码器 / CHAN_D）域；模拟模式把声码器旁路，于是模拟音频既进不来也出不去 HPI。**

## 一、重要更正：VOCODER_IO_SET 位图

此前项目记录与交接里引用的位图「bit7 Voice In(0=Codec/1=File-HPI) / bit1:0 Voice Out(0=Codec/1=File-HPI) / …」**与官方数据手册不符**，它来自厂商 DLL（SCT_Device_T）时代的扩展解释，不是手册定义。

官方 `SCT3258_Packet_Interface.pdf` p.51-52 §1.2.44 的 VOCODER_IO_SET（field **0x3E**）：
- 原文：「It is most used for voice recording and play back. **Currently, this command is only used in DPMR mode only.**」
- 实际位定义：bit7 Reserved；**bit6 MOD_IN**（0=来自 vocoder / 1=来自 MCU，经 CHAN_D）；**bit5:4 ENC_OUT**（语音编码器输出去向）；**bit3 DEC_IN**（语音解码器输入来源）；**bit2 DEMOD_OUT**（解调器输出去向）；bit1、bit0 Reserved。
- 使用示例（Table 1-77）：Local Recording=0x20、Remote Recording=0x04、Local Play back=0x08、Remote Play back=0x40。全部在**声码器 / CHAN_D 数字域**；**没有任何「Voice Out = Codec/File」位**。
- 注：此更正不影响既有 DMR 发射工作——DMR 中继注入走的是 CHAN_D / MOD_IN，与手册一致。

## 二、三层证据

### 层 1 固件反汇编 + 模拟器实跑（最硬，不依赖 SCT 应答）
固件 `Module_current_0.3.66_full_flash_256k.bin`（基址 0x08006000）；模拟器 `research/ChinaMobile-H13/tools/emulator/`（Unicorn 2.1.4，boot 20M 步到稳态）。
- **模拟模式建立函数 `0x08019ffc`**（disasm 第 38906 行起）依次发：`CODEC_SEL(0x0801b588, r0=1)` → **`VOCODER_SEL(0x0801d1c4, r0=16=Analog)`**（第 38954-38955 行 `movs r0,#16; bl 0x801d1c4`）→ `PROCESS_MODE(0x0801c9cc, r0=0x80)` → `ANALOG_SUBAUDIO(0x0801ae48)` → `WORK_MODE(0x0801d2bc, r0=0x43)` → `SQ_LEVEL(0x0801cdb8)`。**全程无 `bl 0x801d0c8`（VOCODER_IO_SET）**。
- 模拟器实跑 `0x08019ffc` 发出的 HPI 包字节：`2d01`(CODEC_SEL) / `1010`(VOCODER_SEL=16) / `1a80`(PROCESS_MODE) / `260000`(ANALOG_SUBAUDIO) / `18430000`(WORK_MODE 0x43) / `6c…`(SQ_LEVEL)——**无 `3e..`(VOCODER_IO_SET)、无 field `00`(SPEECH_SAMPLES)**。
- `0x08008038`（模拟 RX 中段）只发 TI codec 增益寄存器写 `type=0x40`（`00 01 RR GG 00 00`）+ 一次 GPIOF 拉低；无 VOCODER / SPEECH。
- `VOCODER_SEL(0x0801d1c4)` 全局仅 3 调用点：`0x0801365e`/`0x0801a068`（r0=16 模拟）、`0x0801548e`（r0=4 AMBE 数字）；两个模拟点都不碰 VOCODER_IO_SET。
- `VOCODER_IO_SET(0x0801d0c8)` 的全部 11 个调用点都在 0x08015xxx–0x08026xxx 的数字 / DPMR / 录放音路径（r0=0x00/0x04/0x08/0x20），**无一落在模拟函数区（0x08007xxx–0x08008xxx）**。
- 数字对照 `0x08019480`（DMR 呼叫/时隙链）发 `CARRIER_READY 1900` / `DMR_CALL_SLOT 6f80` / `WORK_MODE 18020000`(mode 2)，路径与模拟完全不同。
- （模拟器把 SCT 依赖函数打桩为成功，打桩值是替身；本判定只依赖「MCU 实际写出的命令字节」，不依赖 SCT 应答，证据有效。）

### 层 2 数据手册
- `SCT3258_Packet_Interface.pdf` p.51-52：VOCODER_IO_SET「仅用于 DPMR 模式」，位定义见第一节（无 Voice Out 位）。p.19 Table 1-15：VOCODER_SEL 4=AMBE+2 / 16=Analog。p.10 字段表：CHAN_D=0x01「Encoded voice data」（编码语音，非模拟裸 PCM）；公开 PDF 无 field 0x00 / 无 "SPEECH" 字样。
- `SCT3258_Analog_Setup.pdf` p.15-16：模拟音频硬件通路全在 codec 内部——`CODEC_MIC_GAIN`=左 ADC 前(麦克风)、`CODEC_DEMOD_GAIN`=右 ADC 前(FM 解调信号)、SPK 增益在左 DAC 后(扬声器)；codec 命令经 HPI 下发后由 SCT3258 转成 I2C 送 codec。即 MCU 只经 HPI 配 codec 增益，**从不经 HPI 收解调 PCM**。
- SPEECH_SAMPLES / field 0x00 是厂商工程扩展（见 `H13.md §17.83` 行 5983/5993），其 handler 注册依赖 `VOCODER_IO_SET(0x80) + PROCESS_MODE(3) + WORK_MODE(3,3,0)`（`H13.md` 行 6062/6118），全是数字（WORK_MODE=3）控制态，与模拟（WORK_MODE 字节 0x43 / VOCODER_SEL=16）互斥。

### 层 3 厂商工具反编译源（`public_sct3258/decompiled_SCT_Device/SICOMM/Wangjunhua/`）
- `FormVOCODEUser.cs:650-674,224-234` 的文件路由单选全是**声码器域**（Encode/Decode to/from File = PCM↔AMBE 的声码器收发），无「把模拟解调音频转出」。
- `SCT3252.cs` 模拟相关命令只有 `VOCODER_SELECT{0x10,sel}`(:5836)、`CODEC_SELECT{0x2d,sel}`(:5922)、`ANALOG_CFG{0x3c,…}`(:5972)、`PROCESS_MODE`(:5887)、`WORK_MODE_SET`(:5816)；**无「模拟 Voice Out→File/HPI」命令**。

## 三、镜像（发射侧为何模拟注入 PCM 只得 CW）

HPI → 调制器的唯一通路是 VOCODER_IO_SET bit6 `MOD_IN=1`（经 **CHAN_D** 把编码数据送进**数字 4FSK 调制器**）或工程扩展「Voice In=HPI」（`VOCODER_IO_SET(0x80)`，把 PCM 送进**声码器编码器**）——两者都挂在声码器 / 数字调制链上。模拟模式（VOCODER_SEL=16）声码器被旁路，经 HPI 注入的 PCM 落在一个与模拟 FM 调制器断开的声码器输入上，FM 调制器拿不到音频（麦克风此时也未送入），功放只发未调制载波 = CW。要真正注入模拟音频，只能 (a) 用数字模式让编码器在线，或 (b) 走 codec 模拟口把音频喂到调制器，而不是经 HPI。

## 四、含义与可行替代

- 模拟 RX 玩法（录接收模拟语音、APRS / SSTV 接收解码、窄带扫描/信号记录）**不能靠 H13 本机模块经 HPI 导出音频**。
- 替代路径：
  1. **基地 SDR（RX888 / RSP1，见 `H13.md §16` Radio OS 架构）** 做宽带模拟接收与解码，H13 作随身控制终端——这是推荐的分工。
  2. **codec 模拟口（扬声器 / 耳机）由 Android ADC 采集**：需确认 H13 耳机/附件口电气接到 Android 音频输入（**未证**，属设备外设接线问题）。
- **数字侧**：DMR 接收 PCM / CHAN_D 导出已实机可行，DMR 录制 / BrandMeister 互联不受影响。
- H13 仍可作模拟 FM 接收**监听**终端（本机出声、静噪/亚音）并上报 RSSI/BER，只是不导出音频。

## 五、彻底关闭残留的最短真机无射频验证（RX-only，不发射）

仅在需要 100% 确定时做；须 FM 信号源 + 遵守 bridge/SRAM 原像备份与恢复门、`job.md` 预登记。
1. 设模拟 FM 宽带信道（如 CH11..20，`H13.md:2056` 已标 type=1 模拟 FM），记录基线（模块版本、端口所有者、GPIO、Wi-Fi）。
2. 外部信号源/另一台 HT 在**低功率 + 假负载/大衰减**下，向该频点送已知 1 kHz 单音调制的 FM 信号（H13 本机只收不发）。
3. 进入模拟 RX 后，单变量只发一条 `VOCODER_IO_SET=0x04`（Remote Recording / DEMOD_OUT→MCU，体 `84 a9 61 00 02 00 3e 04`），只读轮询是否出现承载该 1 kHz 的 field `0x01`(CHAN_D) 或 field `0x00`(SPEECH_SAMPLES) 帧。
   - 通过（将推翻本判定）：出现承载 1 kHz 音的 PCM/数据帧。
   - 预期失败（与本判定一致）：只回 `3e 00` ACK、无语音帧。
4. 结束按门恢复：`VOCODER_IO_SET=0x00`、WORK_MODE 复位；校验 bridge flag=0、SysTick 向量、SRAM 逐字节原像、模块重连版本、Interphone 重新独占 `/dev/ttyHS0`、GPIO/Wi-Fi 基线。

## 六、补充闭环（2026-10-15）：其余两条路也已关闭，五角度全封死

本节补三项后续判定（两路离线 + 一次最小可逆真机实测），把"模拟 FM 接收音频能否被 H13 本机取出/录制"彻底收口。

### 6.1 模块 NAND 录音机：只录数字 AMBE，模拟 FM 根本不入【已证】
- 模式门 `VOCODER_SEL`(field 0x10)：数字初始化 `sct3258initcfg` 传 4(AMBE+2)、模拟初始化 `sct3258anainitcfg` 传 16(Analog calls)。进模拟时声码器被设 Analog、不产出编码语音；NAND 的 tape 队列只接收 CHAN_D(编码语音)单元，模拟模式下没有可录的 CHAN_D。出处 `H13.md:2467`。
- tape 写/读/回放单元恒为 CHAN_D(field 0x01，27/36 字节 AMBE)：写路径 0x08023238→0x08017848、读路径 0x08014d20→0x08018e74，`0x0801b404` 只接受 mode 3/4(长度 9*mode=27/36)。存的是 AMBE 编码帧，不是 PCM、不是模拟音频。出处 `H13.md:2542-2544`。
- 实证：所有历史 tape 录音全部来自数字 DMR(例如 `+DMOAUTOUPDATARECORDINFO:group,99,1701,…72…` 是 TG99 DMR 呼叫，即便目录名含 "voice-fm")；档案中无任何一次模拟 FM 产生录音。出处 `H13.md:3808/3849`、captures logcat。
- AT 接口只回录音元数据(voiceId/pack/block/page)，导不出音频载荷；数字 CHAN_D 可经 raw HPI/memread 旁路导出并离线解码成 PCM，模拟 FM 由于全程不经声码器/HPI/CHAN_D，没有任何接口能把它作为录音导出。出处 `H13.md:3784`。

### 6.2 Android 自己的录音（AudioRecord/ALSA）：录不到模块 RX 音频【已证，含实测】
- 两音频域电气隔离：Android(MSM8909+WCD codec) vs 模块(SCT3258+TLV320AIC3204)。Android codec 采集输入只有三路麦克风 AMIC1/2/3(`qcom,audio-routing`)，**无 line-in**，`audio_policy.conf attached_input_devices` 无 LINE_IN。
- 耳机口：WCD 注册了 Headset Jack + headset-mic(ADC2←AMIC2) 能力，但①实体引出未证(`/sys/class/switch`、`/sys/class/extcon` 空，无 h2w，机器胶粘密封未拆)；②该输入是耳机麦克风，与模块 RX 音频无电气关系。
- AUXPCM：`/proc/asound/pcm` 有 device10 AUXPCM Hostless，但物理脚 GPIO59-64 实为 Android 内部 codec cdc_pdm0(非模块)；原厂只用 /sys/boptt/ GPIO 切换，不开 ALSA AUXPCM。
- 真实 DMR RX 实测：device 6/8/11 capture 全 `Captured 0 frames`，麦克风链作阳性对照正常采到 188416 字节。出处 `H13.md §14.10.5`。

### 6.3 最后缺口 AUXPCM 路由的最小可逆实测（2026-10-15，真机，只读+一条可逆 mixer 写）
- 方法：`su -c tinymix "MultiMedia1 Mixer AUX_PCM_UL_TX" 1` 把 AUX_PCM_UL_TX 后端路由到可打开的 MultiMedia1 FE(card0 device0)，`tinycap -D 0 -d 0` 试采集，采完 `tinymix … 0` 写回并核验复原。
- 结果：**device0←AUXPCM 在 8000/48000/默认 三种率下都打不开**：`Unable to open PCM device (cannot open device '/dev/snd/pcmC0D0c': Invalid argument)`、`Captured 0 frames`。对照 `tinycap -D 0 -d 8`(AFE-PROXY TX 标准采集口)**能**打开(证明 tinycap 本身无问题)但同样 0 帧。
- 判定：AUXPCM 后端**不是一条可打开、接到活音源的采集路**，与 6.2 的"AUXPCM 脚在内部 codec、不在模块侧"一致——最后缺口关闭。
- 恢复：mixer 控件复原为 Off(前后核验)、生产 Interphone(PID 2487)全程在跑、设备在线；仅动该一条 ALSA 控件，未碰 HPI/SRAM/GPIO、未发射。

### 6.4 五角度总结论
HPI 导出(§一-五)✗ + NAND 录音(6.1)✗ + Android 标准 ALSA 采集(6.2)✗ + AUXPCM 路由实测打不开(6.3)✗ + 无 line-in(6.2)✗ = **H13 本机无任何通路把模拟 FM(或任意模块)接收音频取到 Android 或数字接口**。根因是两套物理隔离的音频硬件、模块音频只在模块 codec→扬声器。
数字 DMR 例外：语音编码为 AMBE(CHAN_D)可经 HPI 数字链取出、软件解码成 PCM，录音/BrandMeister 网络均可行。
平台结论：模拟信号解码类玩法(APRS/SSTV/录模拟/扫描)归基地 SDR(§16)，H13 定位为 UHF 本机模拟 FM/DMR 语音对讲 + DMR 数字数据/网络终端；模拟 FM 在 H13 仍可收听监控并报 RSSI/BER，只是音频出不了模块。
