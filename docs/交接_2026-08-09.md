## 7. Stable Low-Level Rules

- Bridge flag is `0x2000015C`. MCU function `0x08010A00(r0=baud)` accepts the
  requested baud only while that flag is zero; after bridge entry it forces
  115,200. Set 230,400 before setting the flag.
- The only accepted baud stubs are the 56-byte stack-safe v0.68+ stubs. The
  48-byte v0.63-v0.65 and 52-byte v0.66-v0.67 stubs are permanently forbidden
  because they lose `EXC_RETURN` across a call.
- Before arming any SRAM adapter, read original flag/vector/SRAM bytes, upload
  in words, read back the whole region, validate the expected hash, arm, then
  restore and verify. `H13.md` section 18.27 records the accepted hashes.
- The current automatic timeout adapter is command-tail based. Its temporary
  SRAM footprint must not overlap a capture buffer.
- Stock analogue RF prepare/off one-shot code has explicit hashes in Probe
  reports. Do not substitute an invented GPIO sequence for those helpers.
- `0x0801FF52(code)` leads to the DAC path. The normal RF timing path reads
  the same runtime code from `0x20002DE6`; this is a DAC control point, not a
  calibrated RF power API.

## 8. Recommended Next Work

### Priority 1: isolate the intermittent first HPI codec ACK without RF

Do not keep replaying the full RF-capable VoiceIn sequence. The useful
discriminator is a narrowly scoped no-RF bridge-entry diagnostic:

1. Static-check that the diagnostic does not call the analogue RF-prepare
   helper, CALL_START, PCM write, `DMOPTT=1`, Flash/reset or unknown HPI opcodes.
2. Enter the proven 230,400 bridge, issue exactly the first codec register
   write, capture raw bytes and timestamps, then exit/recover.
3. Compare no-settle, 100 ms settle, and any proposed single timing change in
   separate versioned tests. Do not combine timing, retries and protocol bytes
   in one run.
4. Add short, untruncated phase logs for bridge set, first write flush, first
   byte received and ACK boundary. The Android long report is routinely
   truncated.

Acceptance is a reproducible first codec response contract. A successful
Android write/open or a module-side credit is not sufficient.

### Priority 2: trace the RF/carrier chain statically

Start with the reports above and the recovered MCU disassembly. Identify, with
call-chain evidence, what the analogue RF-prepare helper controls and which
state/GPIO/DAC/RF-timing event is actually asserted by CALL_START. The goal is
to separate these hypotheses:

```text
A. VoiceIn CALL_START can produce a carrier and module PCM is not reaching the modulator.
B. HPI session is accepted but no board TX/PA chain is asserted.
C. TX is active but the receiver channel/CTCSS/measurement setup is wrong.
D. DAC code 1000 is insufficient or differently routed than expected.
```

Do not pick one without evidence.

### Priority 3: future RF acceptance needs an independent observation

Only after Priority 1/2 and a new explicit user authorization:

1. Decide one variable: carrier/PTT observation first, then audio modulation,
   then power calibration. Do not test all three at once.
2. Use an external power meter/load, attenuator/SDR, service monitor, or a
   carefully configured receiver with known frequency/bandwidth/CTCSS state.
3. Record whether carrier exists even with no PCM; then separately record the
   1 kHz modulation. Do not use an SCT credit as a proxy.
4. Keep a short fixed duration and restore production owner, module text,
   channel, GPIO and Wi-Fi afterward.

### Priority 4: retain the DMR external-encoded thread as separate work

The old handoff's S1/S2/S3 plan remains valid after the FM blocker is isolated:
trace the consumer of the `0x200019A8` session record and `0x20000160` state;
compare H13 field-1 framing with the vendor 36-byte API; and trace the power
producer. Do not contaminate this work with fabricated voice data or RF tests.
